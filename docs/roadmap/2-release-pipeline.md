# 2 — Release pipeline and bundle update flow

## Why this exists

[[1-dropin-distribution]] locks the consumption-side design — what `init` would write, how the cascade would work, how wikilinks would resolve across local + bundled docs. This entry is the **publish/update side**: how a bundle gets cut, how a consumer pulls a new one, what the version-bump rules are, and what the failure modes look like.

It's a living plan, intentionally incomplete. Sections marked **decided** are locked; sections marked **open** are where the next iteration happens. Roadmap-1 is the gating decision — if drop-in distribution doesn't ship, this entry stays planning indefinitely.

## The combined release model — *decided in principle*

A host repo would release **one semver version** that covers both its published artefacts (Rust crates, npm packages, container images — whatever the host ships) and the doc-linter ontology bundle. One git tag, one publish pipeline, one version number on the consumer side.

```
v1.4.2
├── Host artefacts published to their respective registries
└── Docs bundle published to the bundle host
```

A consumer pinning host version `1.4.2` gets matching artefacts and matching bundle automatically. Doc/artefact drift is **impossible by construction** — the resolver refuses to fetch a bundle whose version doesn't match the host version the consumer pinned.

### Why coupled

- **Truth coupling**: the docs describe the artefacts. If they ship at different cadences, "the docs say X but the code does Y" becomes a real failure mode. Coupling forecloses it.
- **Single release ceremony**: one tag, one CI run, one release-notes file. No coordination overhead between two release pipelines.
- **Version legibility for the consumer**: consumers reason about "host version 1.4.2" — not "host artefacts 1.4.2 + docs 1.5.0." One number to track, one number to upgrade.

### Why not coupled

(Recorded for completeness — not chosen.) Decoupled would let docs ship a typo fix without an artefact release. The combined model handles this with **patch versions**: a doc-only change becomes `1.4.3`, the artefacts rebuild as no-op, total cost is one CI run. Cheaper than maintaining two release pipelines.

## Lockfile shape — *decided*

A consumer repo would carry two files:

```yaml
# .doc-lint.yaml — intent, hand-edited
extends: example-ontology@^1.4

# .doc-lint-lock.yaml — resolution, generated by `doc-linter update`, committed
example-ontology:
  version: 1.4.2
  bundle_sha256: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
  resolved_at: 2026-05-30T10:13:00Z
```

Every command other than `doc-linter update` reads the lockfile verbatim. Determinism, offline-friendliness, and visible-in-PR upgrades come for free.

CI default: **fail if the lockfile is missing or drifts from `.doc-lint.yaml`.** Forces lockfile commits to be intentional.

### Why lockfile (vs TTL or always-fetch)

Same reasoning every modern package manager has converged on: explicit beats implicit, deterministic beats convenient, version upgrades should be a commit (reviewable, revertible) not a side effect.

## Update flow — *decided shape, open details*

```
doc-linter update                  # bumps to latest matching extends: constraint
doc-linter update --major          # bumps across major versions (requires explicit flag)
doc-linter update --check          # exit 1 if a newer matching version exists, no write
```

`update` rewrites `.doc-lint-lock.yaml`, refetches the bundle into `.doc-lint/cache/`, and runs a full lint pass to surface any breakage from the new version (renamed entities, removed wikilink targets, narrowed allowed-values).

**Open**: should `update` produce a structured diff report (added entities, removed entities, breaking changes) so the resulting commit message can be auto-populated? Useful but adds complexity. Defer to first real upgrade event.

## Publish flow — *open*

Sketch (to iterate on):

1. Maintainer cuts a release: `git tag v1.4.2 && git push --tags`
2. CI on tag push:
   1. Verifies workspace is clean and tests pass
   2. Publishes host artefacts to their registries (existing path)
   3. Runs `doc-linter publish --tag v1.4.2`:
      - Builds the bundle (strips non-public `visibility:` docs, generates sitemap, optionally bakes the graph snapshot)
      - Computes content hash
      - Uploads tarball as a release asset on the same git tag
   4. Updates a manifest endpoint that maps `example-ontology@1.4.2` → tarball URL + sha256

### Open questions

- **Bundle host**: GitHub release assets (free, ACL-aware via the repo) vs. dedicated registry (cleaner consumer UX, more infra). Recommend GitHub release assets initially — zero new infra, falls back gracefully if a custom registry is added later.
- **Manifest endpoint shape**: a static `manifest.json` checked into a `releases` branch, or a dynamic endpoint? Static is simpler and more auditable.
- **Pre-release / RC versions**: do we support `1.4.2-rc.1` for consumer testing before tagging? Probably yes; deferred until a consumer asks.
- **Yanked versions**: a published bundle should be yankable if it ships broken ontology. Mechanism TBD — lockfile resolution should refuse to lock a yanked version, but already-locked consumers should keep working.

## Semver discipline — *open*

The bundle's version is the host's version, so semver bumps follow the host's release rules. But the *ontology* has its own breakage surface that needs explicit semantics:

| Change | Bump |
|---|---|
| Doc text edit, no frontmatter change | patch |
| Add a new entity, value, or synonym | minor |
| Add a new role/kind/lifecycle to allowed sets | minor |
| Rename an entity (with retired-id alias) | minor |
| Rename an entity (no alias) | major |
| Remove an entity, value, role, kind, lifecycle | major |
| Narrow an allowed set (remove a value) | major |
| Make a previously-optional field required | major |

**Open question**: should the linter enforce this on `doc-linter publish` by diffing against the previous release? Auto-block a major-bump-required change from being released as a minor. Useful safety rail; would need a "previous release" reference (e.g. the last git tag matching `v*`).

## Consumer update flow — *open shape*

The expected consumer experience:

```bash
$ doc-linter update --check
example-ontology 1.4.2 → 1.5.0 available (5 added entities, 0 removed)

$ doc-linter update
Resolved example-ontology@^1.4 → 1.5.1
Fetched bundle (sha256:…)
Ran lint pass: 0 issues introduced.
Updated .doc-lint-lock.yaml.

$ git diff .doc-lint-lock.yaml
-  version: 1.4.2
+  version: 1.5.1
```

The "ran lint pass: 0 issues introduced" line is the safety net — if the new bundle removes an entity the consumer's docs reference, the upgrade fails before the lockfile is rewritten, so the consumer repo never lands in a broken state from an upgrade alone.

**Open**: when the upgrade introduces issues, does `update` write the lockfile anyway and let the user resolve? Or refuse and require `--force`? Refuse-by-default is safer; `--force` lets a consumer take the upgrade and then iterate the fix in the same commit.

## Failure modes worth thinking about

Listing the ones that could bite, not yet resolving them:

- **Bundle host outage**: consumer can't fetch, can't lint. Cache should be sticky enough that a cached bundle keeps working indefinitely. Already covered by lockfile model.
- **Hash mismatch on fetch**: bundle content differs from what the lockfile says it should be. Hard fail; suggests tampering or corruption. Don't auto-update.
- **Lockfile + extends drift**: `.doc-lint.yaml` says `^2.0` but lockfile pins `1.4.2`. CI should fail; `doc-linter update` should resolve.
- **Multiple `extends:` (future)**: if we later allow extending more than one bundle, version conflicts between them need a resolution strategy. Out of scope for now (single bundle per repo).

## Out of scope for this entry

- The host artefact publish pipelines themselves — each host already has its own, unchanged by this work.
- Editor integration for showing the resolved bundle version inline (Obsidian status bar, etc.).
- Cross-bundle wikilink resolution (only meaningful if we go to per-context bundles, which is deferred).
