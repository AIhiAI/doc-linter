# Entity — MCP

MCP (Model Context Protocol) is Anthropic's stdio JSON-RPC protocol for exposing structured tools to LLM-driven agent harnesses. doc-linter ships an MCP server via `doc-linter mcp` ([`src/cmd/mcp.rs`](../../../src/cmd/mcp.rs)) so any conformant client — Claude Code, Claude Desktop, Cursor, the opencode harness — can query the [[entity-doc-graph]] through the same typed tool catalog the human CLI surfaces, without spawning a subprocess per query. The operative surface is a catalog of read-only tools: `sql`, `list_entities`, `list_docs`, `list_types`, `list_findings`, `list_modules`, `list_files`, `list_migrations`, `function_context`, `query_similar`, `query_dead_code`, `query_endpoints`, `query_impact`, `query_at`, `query_schema`, `query_saved`, `query_path`, `query_doc`, `query_entity`, `read_source`, and `cluster`. The MCP shape IS the agent ergonomics surface; bad ergonomics here propagate into every downstream harness as worse agent behaviour.

Agents drive the server through the standard MCP handshake: `initialize` (negotiates a `protocolVersion` — the server echoes the client's request, defaulting to `2024-11-05`), then `tools/list` to discover the catalog, then one or more `tools/call` invocations. The transport is line-delimited JSON-RPC 2.0 over stdin/stdout: one request per line, one response per line, notifications carry no `id` and elicit no reply. As of [#214](https://github.com/AIhiAI/doc-linter/issues/214), batched requests (a JSON-RPC array of requests) are also supported — the next protocol revision (`2025-03-26`) requires this. A lightweight `ping` method ([#216](https://github.com/AIhiAI/doc-linter/issues/216)) lets harnesses health-check the server without a full `initialize` round-trip.

The threat model is the operative reason every tool is read-only. The MCP `sql` tool is the only surface that takes untrusted query text — typically generated by an LLM from a natural-language ask — and it accepts exactly one `SELECT` / `WITH` statement that SQLite itself reports as read-only (`sqlite3_stmt_readonly`), so `INSERT`, `DELETE`, `DROP`, `PRAGMA`, `ATTACH` or `WITH ... DELETE` are rejected with a `-32602` invalid-params error. The list-style tools return typed catalog rows directly from the graph and never touch user-supplied query strings. `read_source` is constrained to the repo root via a path-traversal guard ([#211](https://github.com/AIhiAI/doc-linter/issues/211)). The recently-closed [[5-mcp-hardening]] roadmap entry — twelve issues, eight PRs spanning #217 through #223 — closed the silent-failure gaps that an unbiased agent-driven review surfaced: silent empty responses on bogus enum values, `null`-shape returns on unknown ids, an unguarded raw-query tool, and missing read-only enforcement on the source-read path.

Every shipped MCP client speaks stdio, so adopters wire `doc-linter mcp` into a `.mcp.json` entry alongside whatever other servers they run. The same configuration shape works for Claude Code, Claude Desktop, the opencode harness, and Cursor — there is one binary, one transport, one tool catalog. SSE and HTTP transports are deferred until a concrete cross-host use case lands; authentication design follows from there (stdio is per-process, so no transport-level auth applies today).

Authoring rule of thumb: if an agent should be able to do it, it goes through MCP. If a human operator should be able to do it, it goes through the CLI. The two surfaces share their helpers — both ultimately call into the `GraphRead` readers — but they diverge on error semantics. MCP returns JSON-RPC error codes (`-32602` invalid params, `-32601` method not found, `-32700` parse error, `-32600` invalid request) so agents can branch on them without natural-language parsing. The CLI returns human prose so operators can read the error and adjust their next command.
